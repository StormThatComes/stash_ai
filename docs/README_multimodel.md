# Stash AI — current user guide

This guide documents the application's current behavior. For setup,
start with the [project README](../README.md). More specialized
references are linked at the end.

## 1. How it works

Stash AI analyzes VTT and sprites generated by Stash; it neither
opens nor decodes video files.

Supported models:

| Model | CLI name | Legacy model prefix |
|---|---|---|
| JoyTag | `joytag` | `jt:` |
| WD EVA02-Large v3 | `wd` | `wd:` |
| DanbooruTagQuery L/16 | `dtq` | `dtq:` |
| OppaiOracle V1.1 | `oppai` | `op:` |

Models perform inference sequentially. Only one model resides
in GPU memory at a time, while CPU frame preparation may overlap.

Publication always creates shared `ai:` tags and merges compatible
model predictions. Historical model-specific prefixes require
explicit migration and can still be handled by legacy cleanup.

## 2. Input and state database

The default `tagger_sources.sqlite3` is persistent application
state. Among other things, it stores:

- raw inference evidence and aggregates;
- checkpoints for incomplete runs;
- snapshots of published state;
- indexes for resume and fast merging;
- cleanup and recovery records.

The database stores neither images nor the API key. Back it up
together with your configuration.

Update an older supported database explicitly with `--db-update`.
The current schema is **v27**. Do not run an older copy of
the application on the same database after using newer
recovery/cleanup features.

## 3. Resume, restart and checkpoints

Resume is enabled by default in `merged` mode:

```powershell
python .\stash_ai.py --models all
```

For each scene/model pair, Stash AI validates model identity,
configuration and input. If the saved result still matches,
inference is skipped. A compatible partial checkpoint resumes
from the last safely persisted batch.

`--restart` forces fresh inference for the selected scope:

```powershell
python .\stash_ai.py --models wd --scene-id 123 --restart
```

Do **not** use `--restart` just to re-merge saved results,
clean up excluded tags, change publication thresholds based
on cache, or repair hierarchies/marker groups. All of these
have GPU-free modes.

Checkpoints are written every eight batches by default,
on controlled interruption/error and at the end of each
scene. Global `checkpoint_batches` in `tagger_models.yml`
sets the interval; `--checkpoint-batches N` takes precedence.
N must be an integer >= 1; omission retains default 8.
Changing it does not invalidate results or checkpoints.

```yaml
checkpoint_batches: 32
```

### Rebuilding a fresh database: `--db-init`

If the state database was lost but shared AI results remain
in Stash, use:

```powershell
python .\stash_ai.py --db-init --models all --state-db .\tagger_sources_fresh.sqlite3
```

Only a new/empty database and full inference of both outputs
are accepted. Existing results are retained scene by scene
until all selected models complete. Existing `ai:<label>`
assignments and markers titled `[AI] ` with an ownership tag
are adopted. Categories, reserved tags and foreign markers
continue to follow normal publication rules.

Selecting only some models rebuilds results using only those
models; therefore `--models all` is recommended. Resume with
the same database path, model set, and `--scene-id` scope.
The flag can be omitted on resumption; repeating it does
not erase progress. Dry-run simulates reconstruction in
a temporary overlay. See [database initialization](UPGRADE_db_init.md)
for limitations.

## 4. Merge and publication cache

Merge combines saved model evidence with current Stash state
without necessarily loading any models:

```powershell
python .\stash_ai.py --merge-only
python .\stash_ai.py --merge-only --scene-id 123 --dry-run
```

After a successful publication, a compact `merge_check`
is saved. If code/policies, the tag catalog, and scene
state are still compatible, the next run can skip evidence
decoding and publication planning.

Changes to code or publication policy may invalidate
this cache once and require re-merge; this does **not**
automatically require inference.

`--force-merge` forces a recalculation from saved results
and must accompany `--merge-only`:

```powershell
python .\stash_ai.py --merge-only --scene-id 123 --force-merge
```

## 5. Replacing previous results

Each new valid inference result replaces the existing active
result for that model and output kind. Compatible cache reuse
can avoid running the model again. Previously recorded
source-specific prefixes must be migrated to `ai:` using
the [transition-release namespace migrator](../README.md#migration-tools-from-the-transition-release)
with fresh inference; legacy migration commands are no longer
part of the current package.

Known marker intervals always publish an end time.
Occurrence points remain points. Legacy ordinary AI markers
previously stored as points require the separate
[transition-release point migrator](../README.md#migration-tools-from-the-transition-release).

## 6. Thresholds and GPU-free rethresholding

Model thresholds live in `tagger_models.yml`.

### Markers

```powershell
python .\stash_ai.py --models all --merge-only --rethreshold-markers
```

This operation runs no models, uses retained frame results,
rejects insufficient retention, and does not invent missing data.

### Scene tags

```powershell
python .\stash_ai.py --models all --merge-only --rethreshold-scenes
```

Both can be combined:

```powershell
python .\stash_ai.py --models all --merge-only --rethreshold-scenes --rethreshold-markers
```

Changing a scene threshold requires saved observations sufficient
to recalculate eligibility. If a scene/model pair has no evidence
for the requested output kind, it is skipped as having no work;
for example, history from `--markers-only` does not block
`--rethreshold-scenes`.

However, if `result_index` indicates that the result should
exist but the record is missing, or if saved cache is obsolete
or incomplete, the operation still fails **before** applying
threshold changes. `--merge-only` never runs missing inference.
Normal resume can also reuse evidence after safe threshold
changes when all required observations are available.

### Independent evidence retention floors

Configure these separately within `joytag`, `wd`, `dtq`
or `oppai`:

```yaml
scene_cache_floor: 0.20
marker_cache_floor: 0.25
```

Both are optional numbers from 0 to 1, controlling how much
evidence is retained in `merged` mode. Omitting the field
or setting `null` preserves legacy automatic behavior.
The cache records observations down to the minimum of
the configured retention floor and the current support
threshold: `scene_threshold * scene_support_ratio` for
scenes, `marker_threshold * marker_continue_ratio` for
markers. Without temporal rules, use the publication
threshold directly.

Consequently, retention cannot remove evidence necessary
for current publication, but weaker predictions must
still pass the normal eligibility rules before publication.

Example: inference with `scene_threshold: 0.80` and
`scene_cache_floor: 0.20` retains observations from 0.20
plus exact label aggregates. Lowering `scene_threshold`
to 0.40 with `scene_support_ratio: 0.85` requires evidence
down to 0.34, so `--rethreshold-scenes` can use that cache
without loading a model. Lowering it to 0.15 would require
0.1275 and is rejected due to insufficient retained evidence.

Actual floors are saved in `scene_score_floor` and
`marker_score_floor` metadata. Changing retention settings
can invalidate completed inference and partial checkpoints
during normal execution. Fresh inference is then needed
to recover previously discarded observations; merging
and rethresholding cannot reconstruct them. Keep floors
unchanged when only lowering publication thresholds.
Broader retention costs storage and may increase merge
RAM/CPU usage. Fresh inference always persists evidence
under the configured retention rules.

## 7. Temporal rules

`temporal_policy.yml` controls automated post-processing:

- `shared_marker_frames` — combined qualification of compatible
  frames across models;
- `shared_marker_extras` — extras contributed by other models;
- `short_marker_extras` — brief coherent episodes of extras;
- `shared_scene_tags` — additional scene-tag qualification;
- `occurrence_markers` — representative points for scene
  tags without their own marker;
- marker-continuation hysteresis;
- minimum matches and extra coverage requirements.

The temporal engine always runs. `--no-temporal` and the YAML
`enabled` key are removed; individual rules remain configurable.
The historical algorithm is only retained for frozen
cleanup-snapshot replay.

After changing `marker_continue_ratio`, `--merge-only` verifies
that retained marker evidence covers the new continuation
threshold. If the retained floor is higher, inference is
required before publishing that scene, including dry-run.
The effective `marker_threshold` is checked even when
previously rethresholded. Legacy frames without retention
metadata and imported intervals retain historical checks.

`MARKER_TAG_BLOCKLIST` has been retired. Put exclusions in
`marker_core_exclusions.yml` or `scene_tag_exclusions.yml`;
these affect publication but preserve raw cache detections.
Existing checkpoints/cache recorded with an empty blocklist
remain compatible.

The `marker_tag_blocklist` field remains in historical
result metadata; new results store an empty list.
Older cache with a non-empty blocklist requires fresh
inference, because previously rejected detections
are absent from saved frames. `--merge-only` and marker
rethresholding report an error before publishing the
affected scene, including `--markers-only` and `--dry-run`.
Legacy cache without the blocklist metadata also needs
a one-time refresh before normal merge/rethreshold.

Cleanup can still retract votes from previously published
consensus markers without inference: it checks persisted
proofs and restricts changes to published intervals/extras.
Historical publication exclusions remain respected;
cleanup does not add new votes or newly unblocked tags.
Recompute affected scene/model pairs before normal merge:

```powershell
python .\stash_ai.py --models wd --scene-id 123 --restart
```

`--force-merge` cannot restore missing detections.
Imported `separate`-mode intervals retain their historical
behavior. Scene-tag-only operations do not require marker
blocklist metadata.

After changing `scene_support_ratio`, `--merge-only`
recalculates scene statistics from saved frames even
if `scene_threshold` is unchanged. Raw observations
remain in the database, so the old ratio can be restored.
If the newly required support floor is below the
cache retention floor, or required frames are missing,
the scene needs inference before publication.
Legacy aggregates without retention metadata retain
their prior behavior; fresh inference populates
the evidence needed for future rule changes.

**Model scores are not averaged into one probability.**
Per-model sources and confidence values remain distinct.

## 8. Scene tags, markers and Occurrence

In `merged` mode, the shared label is published as
`ai:<label>`. Interval markers derive their start
and end times from VTT samples. An Occurrence marker is
one representative point for an accepted scene tag that
has no corresponding marker interval.

Occurrence:
- is controlled by `occurrence_markers`;
- only uses saved times/observations;
- never guesses times absent from cache;
- respects exclusions, without a per-scene marker-count limit;
- has the technical tag `ai:marker:occurrence`.

See [Occurrence details](UPGRADE_occurrences.md).

## 9. Exclusions

Two main files:

- `scene_tag_exclusions.yml` — global exclusions for scene
  tags, markers, extras and hierarchy creation;
- `marker_core_exclusions.yml` — primary-marker-tag exclusions.

Exclusions apply to regular merge and cleanup modes:

```powershell
python .\stash_ai.py --models all --cleanup-only --dry-run
python .\stash_ai.py --models all --cleanup-only
```

Other cleanup scopes include `--cleanup-markers-only` and
`--cleanup-scene-tags-only`. Cleanup does not load models
or refetch sprites.

## 10. SQL cleanup

`--cleanup-strategy auto` attempts a read-only `querySQL`
operation and falls back to reading scenes when unavailable.
`sql` and `scenes` force the respective paths.

SQL is used **only for reading** IDs and state needed for cleanup.
All Stash modifications go through its API/hooks.

```powershell
python .\stash_ai.py --models all --cleanup-only --cleanup-strategy sql
```

Batch-size defaults:
- `--cleanup-page-size 2000`;
- `--cleanup-write-batch-size 200`.

GraphQL mutations are not automatically retried. If a response
was lost, resuming the same operation first reads current
state and continues with remaining objects.

See [SQL cleanup](UPGRADE_cleanup_sql.md).

## 11. Pending operations and recovery

Publication saves a local plan before mutating Stash.
This allows safe resume of interrupted merge/cleanup operations.

To use a changed policy instead of finishing the old plan:

```powershell
python .\stash_ai.py --abandon-pending
```

You can also abandon an old plan while starting a new operation:

```powershell
python .\stash_ai.py --merge-only --abandon-pending
python .\stash_ai.py --models all --cleanup-only --abandon-pending
```

Abandonment does not undo modifications already made by Stash.
It retains inference results and data needed to reconcile
publication ownership later.

See [abandoning pending operations](UPGRADE_abandon_pending.md).

## 12. Tag hierarchy

All models share `tag_hierarchy.yml`, the union of the
previous four hierarchies: 21,154 unique tags in 92 groups
with unchanged assignments. Categories are published under
shared `ai:category:...` tags. One raw-label entry
defines its parents for all models.

`--hierarchy YAML` specifies the shared file for any selected
model set. `--wd-hierarchy`, `--dtq-hierarchy` and
`--oppai-hierarchy` have been removed. Validation checks
the full YAML and selected models' vocabulary coverage.
Entries from unselected models are allowed but do not
cause their tags to be created by
`--sync-hierarchy-only --create-all-tags` when running
with a subset of models.

Optional `source.tag_count` and `source.vocabulary_sha256`
metadata describe distinct tags in the **entire file**,
not an individual model's vocabulary. Update both fields
or remove both after adding/removing labels. Changing
only grouping does not change the vocabulary fingerprint.

Move custom assignments from `joytag_hierarchy.yml`,
`wd_hierarchy.yml`, `dtq_hierarchy.yml`, and
`oppai_hierarchy.yml` into the shared file.
The updater preserves old local YAML, but the application
no longer reads it. Hierarchy changes do not invalidate
inference cache or require database migration.

Synchronization replaces hierarchy-managed parents
with assignments from current YAML, preserving parents
outside that hierarchy, including user-created categories.
Removing an assignment does not delete the category tag
object itself from Stash.

`parent_sync` has been removed from the schema.
Delete it from custom or locally preserved YAML
before running the current version.

```powershell
python .\stash_ai.py --sync-hierarchy-only --dry-run
python .\stash_ai.py --validate-hierarchy
python .\stash_ai.py --models wd --validate-hierarchy --hierarchy C:/stash_ai/my_tag_hierarchy.yml
```

`--create-all-tags` is only supported with
`--sync-hierarchy-only`.

Exclusions still apply independently to model predictions
and category creation from their vocabularies.
The shared hierarchy skips a label excluded by **all**
models; excluding it in only one model does not remove
the mapping for the others.

`--no-hierarchy` disables model-category synchronization,
but not `m:` marker groups.

## 13. Marker groups

Every managed `ai:` marker may receive an extra group tag:

- `m:<core>` for ordinary markers;
- `m:<core>:occurance` for Occurrence.

The root is `ai_markers`. These groups are organizational
**tags**, not Stash Group objects.

Repair existing markers:

```powershell
python .\stash_ai.py --sync-marker-groups-only --scene-id 123 --dry-run
python .\stash_ai.py --sync-marker-groups-only
```

See [marker groups](UPGRADE_marker_groups.md).

## 14. Dry-run

`--dry-run` writes neither to Stash nor to the persistent
state database. For a current-schema database, it opens
the source read-only and applies planned changes to a
temporary SQLite overlay.

A dry run may still read Stash, download missing model
assets in modes that require them, and perform expensive
merging calculations. Use a small `--scene-id` selection
when evaluating configuration before a large run.

## 15. Network access and retries

Reads and writes use separate retry policies:

- Media GET operations retry transient failures.
- Read-only GraphQL retries timeouts/connection errors and
  HTTP 429/500/502/503/504.
- Actual GraphQL mutations execute only once automatically.

This distinction is deliberate: after a mutation timeout,
the server may already have committed the change.

Media redirects are allowed only within the same Stash
origin, to prevent forwarding `ApiKey` to another host.
GraphQL redirects indicate a misconfigured `STASH_URL`.

## 16. Memory and frame preparation

Defaults:

| Option | Value |
|---|---:|
| `--ram-budget-gb` | 32 |
| `--ram-cache-gb` | 24 |
| `--prepare-workers` | 4 |
| `--checkpoint-batches` | 8 |
| `--prefetch-batches` | 4 |
| `--result-prefetch-batches` | 32 |

Cache memory is allocated lazily and limited to 75% of the
RAM budget. This is **not a hard process-memory cap**:
the model, active tensors, Python runtime and SQLite
also consume memory.

The shared input cache allows later models to reuse
downloaded VTT/sprites during one run while they
remain in cache.

See [performance and memory](UPGRADE_performance.md).

## 17. Merge diagnostics

For forced profiling of saved results without inference:

```powershell
python .\stash_ai.py --merge-only --scene-id 123 --force-merge --profile-merge merge-profile.jsonl
```

`--profile-merge` writes stage/API timings and counters as
JSONL and requires a new output file. `--verbose` prints
additional detail to the console.

If an identical later run does not show expected
`merge_reused`, inspect the `reason` field and
`merge_*` counters.

See [merge profiling](UPGRADE_diagnostics.md).

## 18. Application updates

`update_stash_ai.py`:
- downloads managed application files from one `main` SHA;
- uses fine-grained `GH_TOKEN` / `GITHUB_TOKEN`;
- does not invoke `pip`;
- does not update models, database or `.env`;
- protects locally modified files;
- uses an installation lock and recovery journal.

```powershell
python .\update_stash_ai.py --check
python .\update_stash_ai.py --dry-run
python .\update_stash_ai.py
python .\update_stash_ai.py --recover
```

Locally modified YAML is preserved, with new proposals
saved as `.incoming`. `--overwrite-configs` explicitly
accepts the repository's version. Locally modified code
requires `--force-code`.

## 19. Credential security

Set your own `STASH_API_KEY` in the environment if Stash
requires authentication. The default is empty; the old
fallback has been removed. See [SECURITY.md](../SECURITY.md)
for rotating a historic key.

The updater's GitHub token should be restricted to
this repository with `Contents: read` permission.
