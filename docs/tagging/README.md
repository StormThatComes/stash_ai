Tagging reads Stash VTT files and sprites. Start with [installation](../../README.md#quick-start),
then select a workflow below. Recognition is a separate [explicit command](../facial-recognition.md).

## How it works

Stash AI analyzes VTT and sprites generated by Stash; it neither
opens nor decodes video files.

Supported models:

| Model | CLI name | Legacy model prefix |
|---|---|---|
| JoyTag | `joytag` | `jt:` |
| WD EVA02-Large v3 | `wd` | `wd:` |
| DanbooruTagQuery L/16 | `dtq` | `dtq:` |
| OppaiOracle V1.1 | `oppai` | `op:` |

Models perform inference sequentially. Only one model resides
in GPU memory at a time, while CPU frame preparation may overlap.

Publication always creates shared `ai:` tags and merges compatible
model predictions. Historical model-specific prefixes require the separate
[legacy migration tools](../maintenance/legacy-migrations.md).

## Resume, restart and checkpoints

Resume is enabled by default in `merged` mode:

```powershell
python .\stash_ai.py --models all
```

For each scene/model pair, Stash AI validates model identity,
configuration and input. If the saved result still matches,
inference is skipped. A compatible partial checkpoint resumes
from the last safely persisted batch.

`--restart` forces fresh inference for the selected scope:

```powershell
python .\stash_ai.py --models wd --scene-id 123 --restart
```

Do **not** use `--restart` just to re-merge saved results,
clean up excluded tags, change publication thresholds based
on cache, or repair hierarchies/marker groups. All of these
have GPU-free modes.

Checkpoints are written every eight batches by default,
on controlled interruption/error and at the end of each
scene. Global `checkpoint_batches` in `tagger_models.yml`
sets the interval; `--checkpoint-batches N` takes precedence.
N must be an integer >= 1; omission retains default 8.
Changing it does not invalidate results or checkpoints.

```yaml
checkpoint_batches: 32
```

## Merge and publication cache

Merge combines saved model evidence with current Stash state
without necessarily loading any models:

```powershell
python .\stash_ai.py --merge-only
python .\stash_ai.py --merge-only --scene-id 123 --dry-run
```

After a successful publication, a compact `merge_check`
is saved. If code/policies, the tag catalog, and scene
state are still compatible, the next run can skip evidence
decoding and publication planning.

Changes to code or publication policy may invalidate
this cache once and require re-merge; this does **not**
automatically require inference.

`--force-merge` forces a recalculation from saved results
and must accompany `--merge-only`:

```powershell
python .\stash_ai.py --merge-only --scene-id 123 --force-merge
```

## Thresholds and GPU-free rethresholding

Model thresholds live in `tagger_models.yml`.

### Markers

```powershell
python .\stash_ai.py --models all --merge-only --rethreshold-markers
```

This operation runs no models, uses retained frame results,
rejects insufficient retention, and does not invent missing data.

### Scene tags

```powershell
python .\stash_ai.py --models all --merge-only --rethreshold-scenes
```

Both can be combined:

```powershell
python .\stash_ai.py --models all --merge-only --rethreshold-scenes --rethreshold-markers
```

Changing a scene threshold requires saved observations sufficient
to recalculate eligibility. If a scene/model pair has no evidence
for the requested output kind, it is skipped as having no work;
for example, history from `--markers-only` does not block
`--rethreshold-scenes`.

However, if `result_index` indicates that the result should
exist but the record is missing, or if saved cache is obsolete
or incomplete, the operation still fails **before** applying
threshold changes. `--merge-only` never runs missing inference.
Normal resume can also reuse evidence after safe threshold
changes when all required observations are available.

See [retained evidence and cache reuse](state-and-cache.md) for retention floors,
input verification and the conditions that require fresh inference.

## Results in Stash

In `merged` mode:

| Item | Example |
|---|---|
| Scene tag / marker core | `ai:blue_hair` |
| Marker title | `[AI] blue_hair [jt+wd+op]` |
| Ownership tag | `ai:marker:stash-taggers` |
| Occurrence point | Also has `ai:marker:occurrence` |
| Regular marker group | `m:blue_hair` |
| Occurrence group | `m:blue_hair:occurrence` |
| Marker group root | `ai_markers` |
| Hierarchy categories | `ai:category:...` |

Occurrence groups use `:occurrence`. The one-time spelling migration is
complete; current versions manage only the canonical names.
See [marker groups](marker-groups.md) for details.

## Dry-run

`--dry-run` writes neither to Stash nor to the persistent
state database. For a current-schema database, it opens
the source read-only and applies planned changes to a
temporary SQLite overlay.

A dry run may still read Stash, download missing model
assets in modes that require them, and perform expensive
merging calculations. Use a small `--scene-id` selection
when evaluating configuration before a large run.

## Network access and retries

Reads and writes use separate retry policies:

- Media GET operations retry transient failures.
- Read-only GraphQL retries timeouts/connection errors and
  HTTP 429/500/502/503/504.
- Actual GraphQL mutations execute only once automatically.

This distinction is deliberate: after a mutation timeout,
the server may already have committed the change.

Media redirects are allowed only within the same Stash
origin, to prevent forwarding `ApiKey` to another host.
GraphQL redirects indicate a misconfigured `STASH_URL`.
